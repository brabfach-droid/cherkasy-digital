# Доступ та дані

RLS активовано для всіх таблиць. `user_roles` та `staff_departments` не можна змінювати прямими frontend запитами. RPC `set_staff` доступний лише активному super_admin; перевірка виконується в PostgreSQL. Власник профілю не може змінити user_id, email/blocked, id або created_at. Email синхронізується тригером з Auth після підтвердження зміни.

Application INSERT/UPDATE через REST заборонені. `save_draft`, `submit_application`, `change_application`, `cancel_application` перевіряють користувача, департамент і стан, з row locks. Надсилання перевіряє обов’язкові поля, email, опції, числа, довжину, regex та вкладення на сервері. Номери генерує sequence, не `count()+1`. Відповіді, файли, історія й повідомлення доступні власнику або відповідному працівнику. `viewer` не змінює дані, `editor` не читає заяви. Internal notes приховані від мешканця.

Файли у приватних buckets не мають постійних public URLs. Object path для заяви має `user_id/application_id/random.ext`; Storage policy перевіряє доступ до конкретної батьківської заяви. Metadata guard не дозволяє послатися на відсутній об’єкт чи шлях іншого користувача. Signed URL діє 5 хвилин: отримувач такого посилання може відкрити файл до завершення строку, тому не надсилайте його стороннім. MIME allowlist та max size діють на Storage, розширення/MIME/розмір перевіряються у UI. Antivirus/content-sniffing не підключено.

API тривог викликає лише cron через серверний `x-sync-secret`. Спільний lease у Postgres обмежує повторні виклики різних function instances. Public read дозволено лише для sanitized `api_cache` без токенів. Upstream failure не оновлює `refreshed_at` і не створює false all-clear. За замовчуванням scope — район UID 152 плюс обласна тривога; параметри змінюються в Edge secrets.

Rich text зберігається як Markdown; при відображенні HTML очищується DOMPurify. Не використовуйте raw HTML без sanitizer. External action URLs у публічному UI обмежено HTTP(S), внутрішні notification URLs починаються з одного `/`.

Публічними є лише news/events/site-assets. Завантажені у них зображення можуть бути доступні за відомим URL ще до публікації статті, тому не завантажуйте в них конфіденційні матеріали. Редактор не керує брендинговими assets. Public CMS tables не містять персональних даних заявників.

## Видалення акаунта

Користувач створює `account_deletion_requests`. Адміністратор ставить `processing`, перевіряє політику зберігання і вручну виконує видалення/анонімізацію в SQL Editor та Auth dashboard. Спочатку видаляють приватні об’єкти Storage, потім пов’язані персональні дані та записи, для яких закінчився строк зберігання, і лише потім Auth user. FK на заяви/аудит навмисно не каскадують безконтрольно; Auth deletion може бути заблокований такими зв’язками. Потрібні рішення щодо audit/заяв за реальною політикою, тому універсальний destructive SQL скрипт не додається. Browser не отримує service_role й не видаляє Auth users. Закривайте запит після завершення обробки.

## Межі

Перед публічним використанням налаштуйте SMTP, правові тексти, відповідальні органи, backups і політику даних. Тести перевіряють SQL у PGlite та локальний frontend. Реальні hosted Auth, Storage HTTP, cron і Edge Function з вашим токеном потребують перевірки у вашому проєкті. Автоматичних SMS/BankID/Дія/ЕЦП, платежів, антивірусу чи e-mail розсилок немає. Усі системні повідомлення — у внутрішньому центрі сповіщень.
